# 案例研究：定位并修复 LLM 的"格式正确但内容幻觉"问题

> 一次关于 LLM grounding（知识锚定）失败模式的实证排查记录。
> 涉及：根因定位、可复现实验、系统性修复、跨模型对照验证。

---

## 1. 问题现象

生成的微信小程序代码在浏览器内预览时图片正常显示，但**导入真机小程序后图片全部加载失败**。

两个环境表现不一致，是排查的第一个关键线索——浏览器预览端的 `render_wxml.py` 给所有 `<image>` 标签转换出的 `<img>` 加了 `onerror` → 占位图回退，**这个兜底逻辑掩盖了真实的死链**，而真机小程序里没有这层伪装。换句话说：bug 一直存在，只是预览环境的容错把它"藏"起来了。

## 2. 根因定位

逐层排查后，定位到 `gemma_core/prompt_builder.py` 里一条具体的错误指令：它教模型把 Unsplash 图片 ID 生成为 **`photo-{16位小写十六进制}`**（如 `photo-a1b2c3d4e5f6a7b8`），而 Unsplash 真实 ID 格式是 **`photo-{10~13位时间戳}-{12位十六进制}`**（如 `photo-1514362545857-3bc16c4c7d1b`）。

模型严格执行了这条指令——格式完全自洽、肉眼难辨，但对应的 URL 在 Unsplash 服务器上根本不存在。

## 3. 一个更深的问题：连"参考样例"本身都没被验证过

把指令改成正确格式后，自然的下一步是：在提示词里放入"图片库"供模型抄写。但抄哪些 ID？最初的直觉是复用项目里已有的"黄金样例"（19→23 个预生成场景语料）——因为它们"看起来是正确的参考"。

**实测结果推翻了这个假设**：用 `urllib.request` 对 `images.unsplash.com/photo-{ID}` 发 HTTP HEAD 请求逐个验证后发现——

| 来源 | 抽查/全量 | 死链数 |
|---|---|---|
| `coffee_shop` 黄金样例 | 全部 8 个 | **8 个全部 404** |
| `ai_wedding_studio` 黄金样例 | 全部 10 个 | 5 个 404 |
| `michelin_restaurant` 黄金样例 | 全部 12 个 | 1 个 404 |
| 自己凭训练记忆新写的"图片库" v1 | 54 个 | 13 个 404（重测 5 次结果一致，非限流） |

**关键认知**：这些"黄金样例"本身不是人工精心挑选的金标准模板，而是早期模型生成结果中提取出来的产物——它们继承了和 bug 完全相同的"格式对、内容编"问题。**用一个未经验证的幻觉去修复另一个幻觉，只会原地打转。**

## 4. 跨模型对照实验：数据集大小能否解决这个问题？

一个自然的假设是："如果换一个训练数据更丰富的模型，是不是就能凭记忆给出真实存在的图片 ID？"

设计了一个干净的对照实验（排除提示词中任何示例 ID 的干扰，纯靠模型自身训练记忆）：让**当前生产模型 `gemma-4-31b-it`** 和**参数量、训练数据规模都大得多的 `gemini-2.5-flash`**，各自报出 6 个"确信真实存在"的 Unsplash photo ID，逐一 HTTP 实测验证。

| 模型 | 命中率 | 现象 |
|---|---|---|
| `gemini-2.5-flash`（数据集远大于 Gemma） | **0/6 = 0%** | 全部编造；6 个 ID 的时间戳全部诡异地聚集在 2023-2024 年区间，明显是在"生成看起来合理的随机数"，而非回忆 |
| `gemma-4-31b-it`（项目生产模型） | 3/7 ≈ 43% | 命中率反而更高；但错误样本极具揭示性（见下） |

`gemma-4-31b-it` 给出的两个错误 ID 堪称"格式记忆与内容记忆分离"的教科书案例——它们与图片库中的真实 ID **时间戳完全一致，仅十六进制后缀不同**：

```
模型说：photo-1517841905240-472988be584a   （不存在）
真实 ： photo-1517841905240-472988babdf9   （存在）

模型说：photo-1498050108023-c5249f401fc5   （不存在）
真实 ： photo-1498050108023-c5249f4df085   （存在）
```

**结论**：训练数据规模与"能否准确复述某个具体外部事实"几乎无关——这正是当前所有 LLM 共性的 grounding 短板，模型对"格式长什么样"的记忆远强于对"某个具体实例是否真实存在"的记忆。靠堆数据集或换更大的模型都无法绕开这个问题；**唯一可靠的解法是把"事实性查证"从模型生成过程中剥离出来，交给确定性的外部校验**。

## 5. 修复方案：人工核验的"知识锚定层"

把模型从"自由发挥的生成者"改造为"从可信源复制的执行者"：

1. 用 `urllib.request` HEAD 请求逐个核验候选图片 ID 是否真实返回 HTTP 200
2. 把验证通过的 ID 按使用场景（美食/咖啡/时尚/科技/商务/人物/婚礼/酒店/健身共 9 类，58 个）写入 `prompt_builder.py` 的常驻提示词
3. 明确指令："必须从图片库选取，不可自创 photo ID"——把生成自由度精确地限制在"已验证安全"的范围内
4. 回头修复全部受影响样例：`coffee_shop`（8 个）、`ai_wedding_studio`（5 个）、`michelin_restaurant`（1 个）、新建样例 `luxury_service`（2 个）

修复后做了一次全量审计——对项目中**全部 38 个唯一 Unsplash 图片 ID（96 处引用）** 做 HTTP 实测，**100% 返回 200**。

## 6. 这次排查沉淀下来的可复用方法论

1. **环境差异是线索，不是噪音**——浏览器预览正常、真机失败的差异，直接指向"某处存在兜底逻辑掩盖了真实问题"
2. **"格式校验通过"≠"内容真实"**——对涉及外部资源引用的生成内容，格式正则校验只能筛掉明显错误，无法验证语义真实性
3. **不要信任"看起来权威"的参考源**——黄金样例、训练记忆、更大的模型，本质上都是同一类不可靠信息源的不同形式；唯一可信的验证方式是对外部世界做确定性查证（HTTP 请求、数据库查询等）
4. **修复要做到"系统性闭环"**——不是头痛医头地替换报错的那一个 ID，而是审计全部引用源（提示词模板 + 全部黄金样例），确保不会在别处复现同一类错误

---

*本案例的全部实验代码、原始测试数据均可复现：核心方法是对 `https://images.unsplash.com/photo-{ID}?w=80&q=40` 发送 `HEAD` 请求并检查 HTTP 状态码。*
